Aeolus uses a 70mm electric ducted fan (EDF) rather than a rocket motor — the defining constraint of the whole project. A throttleable EDF makes controlled ascent and hover possible without the field clearance and irreversibility of a rocket motor, but it also means propulsion isn't a fixed impulse curve: thrust has to be actively controlled throughout flight.

The EDF itself was selected by trading thrust against mass, not just picking the highest static thrust available (see [EDF Selection](#edf-selection)). Delivering that thrust reliably meant characterizing the motor's actual behavior on a test stand — thrust and current draw were measured across the throttle range, revealing real limitations like a thrust plateau above 70% throttle from unconfigured ESC timing, and voltage sag under peak load severe enough to motivate a battery chemistry change (see [Thrust Characterization](#thrust-characterization)). And because open-loop throttle doesn't track motor RPM directly — voltage sag, ESC nonlinearity, and load all shift the throttle-to-RPM relationship — closed-loop RPM control was necessary to hold a commanded thrust setpoint consistently (see [RPM Governor](#rpm-governor)).

Two things fall out of this data.

**The plateau is an ESC limit, not an aerodynamic one.** Thrust stops rising above 80% throttle — 1775 g at 80%, 1774 at 90%, 1776 at 100% — and RPM flattens with it near 38,600. Current sits at 53 A across all three. The last fifth of throttle travel does nothing whatsoever, which means the usable command range is 0–80%, not 0–100%.

**Thrust-to-weight is 1.23.** Peak measured thrust is 1776 g against a 1444 g vehicle. Hover therefore sits near 64% throttle and roughly 34,900 rpm — about 90% of the achievable RPM. That leaves only 0.23 g of upward acceleration authority in reserve, and it is the single number that most constrains how aggressively the altitude loop can be tuned. It is also why the plateau matters: the margin that exists is entirely below the point where the ESC saturates.

## Thrust from RPM

A ducted fan's thrust scales with the square of its speed. The flight code inverts that relationship so the altitude controller can command a *thrust* and have the governor chase the corresponding *RPM*:

$$\mathrm{RPM} = \sqrt{k\,T}, \qquad k = 8.61 \times 10^{7}$$

# RPM Governor
The simple way to control thrust is by setting throttle; it is what the ESC takes as an input. However, this is inconsistent as it depends heavily on battery voltage among other factors. This is why I decided to control RPM instead of throttle—the same motor RPM will produce the same thrust. To do this, I implemented a feed-forward PI controller that adjusts throttle in real time to match the measured RPM to the target RPM.

First, the [thrust/rpm/throttle data was used](https://www.desmos.com/calculator/udqv0vhbat) to predict RPM based on throttle and voltage.
> ```cpp
> predictedThrottle = K_THROTTLE_RPM * EDF_V_REF/clamped_voltage * targetRPM;   //feedforward
> ```
The PI controller makes adjustments on top of this initial feedforward value.
<Dropdown title="RPM governor code">
```cpp
  float error = targetRPM - currentRPM;

  float Kp_eff = RPM_KP * EDF_V_REF / clamped_voltage;            //voltage-based gain adjustment
  float Ki_eff = (fabsf(error) < RPM_I_GATE_RPM) ? RPM_KI : 0.0f; //integral gate
  changeGains(Kp_eff, Ki_eff, RPM_KD);

  float rawRate = (currentRPM - prevFilteredRPM) / dt; // RPM/s
  prevFilteredRPM = currentRPM;
  float alpha_d = 1.0f - expf(-dt / RPM_D_FILTER_TAU_S);
  filteredRate = alpha_d * rawRate + (1.0f - alpha_d) * filteredRate; //ema filter

  float corr_throttle_pct = rpmGovernor.update(error, dt, filteredRate);
  predictedThrottle = K_THROTTLE_RPM * EDF_V_REF/clamped_voltage * targetRPM;   //feedforward
  setThrottle(predictedThrottle + corr_throttle_pct);
```
(Uses the PID implementation I made—covered [here](./control#pid-controller))
</Dropdown>

Both halves of the loop are scheduled on voltage, not just the feedforward. `Kp_eff = RPM_KP * EDF_V_REF / V` scales the proportional gain by the same ratio, so as the pack sags from 24 V to 21.8 V the correction keeps the same authority in RPM terms rather than quietly weakening exactly when the feedforward is working hardest.

## Cleaning Up the RPM Signal

RPM comes from counting pulses on the ESC output wires, which is a noisy way to measure anything on a vehicle carrying a 53 A motor. Early testing showed both jitter and occasional large spikes, and the governor cannot tell a real transient from a bad pulse. Three stages sit between the sensor and the loop, in a deliberate order:

**1. A plausibility gate, first.** Any sample implying an angular acceleration above 300,000 RPM/s is rejected outright — the plant has never demonstrated anything close, so such a reading is a measurement artifact by definition.

The ordering is the interesting part. A median filter is the obvious tool for spikes, and it is genuinely robust to *isolated* outliers. But it is not robust to a *burst*: four bad samples inside a seven-sample window out-vote the three good ones and the median happily returns garbage. Putting the gate first means a burst is discarded before it can ever reach the window.

That gate has its own failure mode, and it is guarded too. If the stored reference ever goes stale, every subsequent real sample looks implausible against it and the gate locks out the true signal permanently. So after five consecutive rejections it force-accepts, on the reasoning that five straight rejections is better explained by a bad reference than by five straight bad pulses.

**2. A seven-sample median**, which now only has to handle what the gate lets through.

**3. An exponential filter with a recomputed coefficient.** Rather than a fixed smoothing constant, $\alpha$ is derived from the actual elapsed time each cycle:

$$\alpha = 1 - e^{-\Delta t/\tau}, \qquad \tau = 15~\mathrm{ms}$$

A fixed $\alpha$ silently changes the filter's time constant whenever loop timing jitters, which on a system also running attitude estimation at 200 Hz it does. Deriving $\alpha$ from measured $\Delta t$ holds the time constant at 15 ms regardless.

## Tuning

The governor started as a full PID. The derivative term was removed, and the reason is worth stating: the EDF's own response lag meant the D term was reacting to changes the motor had not finished making, and it drove oscillation rather than damping it. Dropping to PI made the response visibly smoother.

<figure class="not-prose my-6 mx-auto max-w-xl">
  <img src="/assets/aeolus/propulsion/governor-pi-vs-pid.webp" alt="Governor response with and without the derivative term." class="w-full rounded-lg" loading="lazy" decoding="async"  width="1400" height="928" />
  <figcaption class="mt-2 text-[11px] text-slate-500 dark:text-slate-400 text-center">Governor response with and without the derivative term.</figcaption>
</figure>
 The derivative plumbing is still in the code — filtered rate and all — with the gain set to zero, so it can be reinstated without rewriting anything.

The integral term is gated rather than merely clamped: `Ki` is active only when the error is under 1500 RPM. During spool-up the error is enormous and persistent, which is exactly the condition that winds an integrator into saturation. Switching it off until the error is small means it never accumulates during the transient it cannot help with, and only engages for the steady-state offset it is actually there to remove.

## Open: Sensor Interference

On 27 August the RPM sensor picked up interference during the first flight of the day, producing an oscillating throttle. The filtering above handles noise on a signal that is fundamentally sound; it does not help when the pickup itself is being corrupted. This is unresolved, and it is a wiring and shielding problem rather than a software one.
